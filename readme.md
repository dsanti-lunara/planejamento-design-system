
# Planejamento Analytics Design System (AeC)

This is **Planejamento Analytics'** design system (AeC) — a shared visual and interaction language for every report and product the area builds, not a system for a single product. Different projects can differ in goals, audience and complexity, but must stay visually recognizable as the same ecosystem: colors, typography, navigation, information density, filters, tables, indicators, charts, system states, and interaction patterns are shared.

**NEXO** (analytics/reporting portal — KPI dashboards, tabular "tabelão" reports, deployment/publication tooling, access management, system-health monitoring) is the system's most complete reference implementation and the source of most of the component inventory below — treat it as an *evolution and application* of the design system, not the only product it serves. The **Relatório Padronizado Claro Brasil** and future Planejamento Analytics products share the same core language (foundations, navigation/inputs, feedback/data-states, data display, data-viz, templates/shells); a product may add specialized components only where its context genuinely requires it, built on these same tokens rather than as a parallel system.

**Before adding anything new**: audit what already exists. Don't recreate mature components — evolve the closest existing one, preserving compatibility, rather than starting a duplicate family.

## Contrato atual do MVP (fonte de verdade)
O Nexo publica produtos de dois tipos apenas — **Power BI** e **Projeto Nexo** — direto em **Produção**, sem etapas intermediárias:
```
Produto
├── Power BI        (link corporativo → validar → publicar)
└── Projeto Nexo    (ZIP → validar → publicar)
```
**Acesso**: Hominum → CR + FUNCAORM → Regras → Produtos liberados. Não existe cadastro geral de usuários, grupo manual, papel Viewer/Analyst, lista manual de leitores, "usuário elegível", solicitação de acesso pelo usuário nem aprovação por owner.

**Admin** (rota `/admin/*`): Produtos · Acessos · Publicações · Auditoria · Utilização · Saúde · Comunicados.
- **Acessos**: Overview · Regras de acesso · Exceções · Administradores.
- **Produto** (detalhe): Geral · Responsáveis · Acesso · Conteúdo · Publicações · Saúde. (Sem abas "Releases" ou "Deployments".)
- **Publicações**: uma publicação = um evento direto em Produção. Sem DEV/HML/PRD, sem etapas de homologação, sem aprovador, sem wizard de 7 passos.
- **Utilização**: Visão geral · Acessos nominais (histórico completo, sessões, heartbeat, exportação de todos os registros filtrados, paginação server-side).
- **Auditoria**: log de ações administrativas — separado da Utilização (que é consumo/uso de produto, não ação administrativa).

Isto é a arquitetura vigente. Qualquer referência a DEV/HML/PRD, homologação, aprovação/aprovador, wizard de publicação, telas "Releases"/"Deployments", cadastro geral de usuários, grupos manuais, papéis Viewer/Analyst ou fluxo de solicitação/aprovação de acesso é **histórico pré-pivot** — ver "Deprecated / Histórico de decisão" nas notas de cada grupo de componentes abaixo — e não deve ser reintroduzida em telas ou componentes novos. `templates/` já reflete este contrato; `audit-telas-nexo.md` documenta a auditoria feita para alinhá-lo.

## Content fundamentals
Copy is in **Brazilian Portuguese**, written in a technical, operational register — third person / impersonal ("Mostrando 1–20 de 240", "Ver análise detalhada"), not a conversational "você". Labels are precise and domain-specific (KPI names, "Vigente", "D-1", "Consolidado") rather than friendly or marketing-toned. No emoji anywhere in copy or UI. Numbers use Brazilian formatting (comma decimal, dot thousands: "126,3", "1.204.387"). Microcopy favors compact, information-dense phrasing over conversational filler — status/state language ("Homologado", "Experimental", "Arquivado") is administrative, not playful.

## Visual foundations
- **Color**: white and very-light-blue surfaces; navy for text; blue reserved for actions/links. Green/red/orange are used strictly to encode data states (positive/negative/warning) — color is never the only signal (paired with icons/labels). Two theme modes exist (light default, dark prepared) via `:root[data-theme="dark"]`.
- **Type**: Inter for UI text (sans), Plus Jakarta Sans for display/brand moments, JetBrains Mono for tabular/numeric and code-like data. Hierarchy is compact — sized for high information density, not marketing scale.
- **Corners**: discreetly rounded, small radii — not pill-shaped, not sharp.
- **Borders**: subtle, low-contrast; used to separate dense table/grid regions.
- **Shadows**: minimal — elevation is mostly conveyed by surface tone/border, not drop shadow.
- **Backgrounds**: flat surfaces only — no photography, gradients, illustration patterns, or textures in the working UI. A small set of state illustrations exist for empty/error/403/404/maintenance/archived screens (see Iconography).
- **Animation**: fast and subtle only — no bounce/elastic. Tokens in `tokens/motion.css` (`--duration-instant` 80ms, `--duration-fast` 120ms, `--duration-standard` 200ms, `--ease-standard`, `--ease-out`, `--scale-pressed` 0.98). The `.ds-interactive` class (in `tokens/base.css`) applies real hover elevation, press scale/darken, and a focus-visible outline on `Button`/`ActionIconButton*`; see guidelines/motion.html.
- **Layout**: fixed shell (sidebar + header), content flows Shell → Contexto → KPIs → Análise → Tabelão → Inteligência. Reference viewport is desktop 1920×1080. Contexts: Dia/Período, D-1/Vigente.

## Iconography
Icons are custom line-style SVGs extracted from the Figma file (`assets/icons/icon-data.js` + `Icon.jsx` wrapper covering nav, chevrons, search, calendar, play, data-state glyphs). No icon font, no emoji, no unicode-glyph icons. State/empty screens use small custom illustrations (`components/feedback/IllustrationSystem*.jsx`) rather than photography or stock art.

### Consolidation note
`navigation/` and `navigation2/` were two parallel sidebar/topbar families (one from Figma's Foundations page, one from NEXO-*) that duplicated the same concepts under different names. They're now one family under `navigation/`.

**Shell unification (portal + admin, topbar)**: `NAVSidebar`, `NavigationPortalSidebar`, `NavigationAdminSidebar`, `NavigationPortalTopbar` and `NavigationAdminTopbar` were five components independently re-drawing the same brand mark, user-menu block, and search box / notification bell markup already covered by `SearchGlobalSearch` / `FeedbackNotificationBell`. Replaced by `NavTopbar` (`variant="portal"|"admin"`) and `ShellPortal`, composed from atoms instead of inline duplication.

**NavSidebar (rebuilt from the real Figma "Navigation/Sidebar" family)**: the sidebar previously shipped as a fictional NEXO-branded `variant="portal"|"admin"` mockup with no Figma source. A second, authoritative "Navigation/Sidebar" component (4 variants: Layout × Environment) surfaced from the Claro-branded "Planejamento Analytics" Figma file — the real client-facing design, complete with the actual `assets/logos/claro-logo.svg` mark. `NavSidebar` was rebuilt against that source and is now the single sidebar component: `collapsed` (Layout expanded/collapsed) and `embedded` (Environment standalone/embedded — embedded drops the logo for a plain product-name header and hides "Voltar ao Portal"). `NavBrand` now renders the Claro lockup (scaled down for the collapsed rail, matching the source) instead of the placeholder Nexo mark. The old portal/admin item list, help panel and user-menu footer were dropped from the sidebar — `NavTopbar` already carries the user menu, so no functionality was lost — matching the real design exactly rather than inventing sidebar chrome. `ShellPortal` updated to the new props. A `logo` override slot was later added so a host product can swap the header mark entirely (e.g. `templates/portal-home` passes the real NEXO lockup, since that template recreates NEXO's own portal home, not the generic Claro-sourced sidebar) without forking the component or losing the Claro default for everything else. A `showUtility` toggle (default true, alongside the existing `showBackToPortal`) was also added — the "UTILITÁRIOS" block and "Voltar ao Portal" footer are Claro-source-specific and don't belong on every host (the portal home template turns both off), and leaving them on unconditionally was pushing the sidebar's natural height well past the viewport, forcing an unwanted scrollbar. A `bordered` toggle (default true) was added too — NavSidebar's own rounded border/inset shadow is correct when it's the whole sidebar, but doubles up when a host composes it as just the top segment of a taller panel (portal home stacks a help-panel card and a user-menu row below it inside one bordered column); with `bordered` left on, the two borders end at different heights and the sidebar reads as disconnected floating fragments instead of one panel.

**Fluid-container fixes (ProductCard, HomeCategoryTile, HomeAnnouncementItem)** — audit of `templates/portal-home`. All three carried Figma's fixed text-box widths (`width: 182/174/160` on ProductCard's name/description, `width: 190` on HomeCategoryTile's label/count, `width: 520` on HomeAnnouncementItem's title/description/date) plus `flexShrink: 0`, so in a fluid `grid`/`flex` container the text boxes stayed at their Figma width and spilled out of the card — producing a page-wide horizontal scrollbar and text running past card borders. All are now `width: "100%"` with `minWidth: 0` on the growing text column. `lineHeight: "100%"` (Figma's literal export) was also replaced with real line-heights (1.3–1.4) since these strings genuinely wrap; ProductCard descriptions are line-clamped (3 lines featured, 2 lines catalog) so a long description can't break the fixed 250px card height, its featured header is `minHeight: 72` instead of a clipping fixed 72, and its bottom row (category chip + access) is `marginTop: auto` so it sits at the card's bottom edge. HomeAnnouncementItem is `minHeight: 112` (was a fixed 112 that clipped a two-line description + date) and top-aligned. Two ignored props were also fixed in ProductCard: the featured/catalog category chip was hardcoded to `category="planejamento"` (now reads `category` + a derived `categoryLabel`), and `tags` was never read at all — the tag row always rendered "Claro / Intraday / +2" (now renders the `tags` prop, string or array, falling back to the Figma default). Do not reintroduce pixel text widths when re-extracting these families from Figma.

**Content-driven / fluid rebuilds (ProductDetailHeader, ProductAccessState, ProductOwnerCard, ProductResourceLinkRow, NavigationBreadcrumb, ShellPortal)** — audit of `templates/detalhe-produto`. Each of the four product families was a set of near-identical Figma-literal bodies with hardcoded copy and fixed frames (ProductDetailHeader: 6 access×favorite bodies, 1131 lines, category/tags/status/action labels baked in; ProductAccessState: 640×420 with `whiteSpace: nowrap` copy; ProductOwnerCard: 520×112 with raw `rgb()` literals and fixed "AF" initials; ProductResourceLinkRow: 3 bodies at 760×104). All are now one fluid `width: "100%"`/`minWidth: 0` implementation whose `access`/`state` variant supplies only *defaults* — every string is a prop, and real handlers exist (`onPrimaryAction`, `onFavoriteToggle`, `onAction`, `onClick`, `onContact`). `NavigationBreadcrumb` gained an `items` array prop that replaces the three hardcoded Figma trails (wrapping crumbs, last = current, others clickable); `ShellPortal` gained `children` (replaces the MAIN CONTENT SLOT placeholder), `fill` (viewport-sized instead of the fixed 1440×900 spec frame), `breadcrumbSlot` and sidebar/topbar passthrough, so pages compose it instead of re-drawing the shell inline. Do not reintroduce fixed frames or hardcoded copy when re-extracting these families from Figma.

## Data semantics
Planejado/realizado/recebido/atendido/desvio read consistently across every report via one semantic family in `tokens/fig-tokens.css` (light + dark modes), never raw hues: `--color-data-plan` (planejado), `--color-data-actual` (realizado), `--color-data-received` (recebido), `--color-data-attended` (atendido), `--color-data-positive`/`--color-data-negative` (desvio favorável/desfavorável), `--color-data-attention` (atenção/warning), `--color-data-forecast`, `--color-data-critical-band`, `--color-data-heatmap-{high,low,risk}`, `--color-data-series-{1..4}` (chart series order). Components must reference these, not raw `--blue-600`/`--green-500` etc., so a report can't drift from the shared reading of a metric. (Removed `--data-plan`/`--data-realized`/`--data-secondary`, an older unused, dark-mode-less duplicate of this family.)

`tokens/fig-tokens.css` (colors, spacing, radius — from Figma Variables, light + dark mode), `tokens/fig-typography.css` (text styles), `tokens/fonts.css` (`@font-face`), `tokens/motion.css` (duration/easing), `tokens/elevation.css` (shadow scale), `tokens/base.css` / `tokens/typography.css` (hand-authored aliases). `--font-bold`/`--font-medium`/`--font-regular`/`--font-semibold` (Figma's per-weight family names) resolve to the uploaded "Inter" family; pair them with a numeric `font-weight` (400/500/600/700) to get the intended weight, since Inter ships as one variable-style family rather than separate PostScript names per weight.

`ui_kits/portal-relatorios/` — NEXO reporting portal shell (sidebar, header, KPI/analysis/tabelão flow) built from `ShellPortal` + composites. This is a NEXO-specific application of the shared system, not the system's boundary — a Relatório Padronizado Claro Brasil (or any future report/product) kit would live alongside it, reusing the same tokens and core component families.

## Index
- `styles.css` — global CSS entry point (imports all tokens/fonts)
- `tokens/` — colors, typography, spacing, radius tokens + font-face
- `components/` — reusable primitives, grouped as above
- `assets/` — logos (`logos/`), fonts (`fonts/`), icon data (`icons/`)
- `guidelines/` — foundation specimen cards (color, type, spacing, radius, density, brand)
- `ui_kits/portal-relatorios/` — full portal screen recreation
- `SKILL.md` — Claude-Code-portable skill wrapper for this system

## Caveats
- No company/product logo existed in-source for "Planejamento Analytics" itself — the brand mark used throughout is NEXO's (the product), plus AeC/Claro/Planejamento Analytics as partner marks; no wordmark was invented.
- Legacy chart family intentionally excluded (see above).
